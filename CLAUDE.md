# CLAUDE.md

Guidance for Claude Code working in this repo.

## Repository purpose

A list of public IP ranges per service provider (Google, AWS, Microsoft, Cloudflare, OpenAI, etc.), refreshed every 4 hours by a GitHub Action and committed back to `main`. Consumers reference the raw `.txt` files via `raw.githubusercontent.com` URLs (see [README.md](README.md)). Licensed under [MIT](LICENSE).

## Architecture

Each provider lives in its own top-level directory (e.g. [google/](google/), [openai/](openai/), [devolutions/](devolutions/)) with exactly four files:

- `downloader.sh` — fetches and normalizes the raw addresses
- `ipv4.txt` / `ipv6.txt` — parsed CIDR list, one per line
- `ipv4_merged.txt` / `ipv6_merged.txt` — same list reduced to the smallest set of CIDRs (auto-generated, not produced by `downloader.sh`)

Plumbing that ties it together:

- [utils/merge.py](utils/merge.py) — thin wrapper around `netaddr.cidr_merge`. The workflow runs it for every `ipv4.txt` / `ipv6.txt` to produce `_merged.txt` siblings.
- [utils/providers.json](utils/providers.json) — single source of truth for provider directories and their display names. New providers MUST be added here.
- [utils/render_readme.py](utils/render_readme.py) — generates the provider table and counts in [README.md](README.md) between `<!-- BEGIN AUTO:* -->` / `<!-- END AUTO:* -->` markers. Idempotent — safe to re-run. Never edit between those markers by hand.
- [all/](all/) — aggregate of every provider's IPs. Generated by `cat`-ing all `ipv4.txt` / `ipv6.txt` files together, then merging.
- [.github/workflows/update.yml](.github/workflows/update.yml) — runs `find . -name downloader.sh | sort -h` and executes each one on `cron: '8 */4 * * *'` and `workflow_dispatch`. After downloads it builds `all/`, runs the merge, runs `render_readme.py`, then commits.

The top-level `ipv4.txt`, `ipv4_merged.txt`, `ipv6.txt`, `ipv6_merged.txt` are legacy/example files — not used by any tooling. Don't confuse them with the per-provider files.

### The `downloader.sh` contract

Each downloader is a self-contained bash script invoked from **either** the repo root (the GitHub Action) **or** its own provider directory (local development). It must write the provider's `ipv4.txt` / `ipv6.txt` correctly in both cases. The convention:

```bash
[ -f "downloader.sh" ] && cp /tmp/<name>-ipv4-final.txt ipv4.txt || cp /tmp/<name>-ipv4-final.txt <provider>/ipv4.txt
```

The presence of `downloader.sh` in the current directory tells the script it was invoked from inside the provider dir; otherwise it assumes repo root and prefixes with `<provider>/`. New downloaders must follow this idiom or they will silently misbehave under one of the two invocation modes.

Other shared conventions:

- `set -euo pipefail` and `set -x` at the top
- DNS lookups go through `dig +short {A,AAAA} <domain> @8.8.8.8` (explicit resolver to avoid CI DNS quirks)
- Bare IPv4 addresses are upgraded to `/32`, bare IPv6 to `/128` via `sed`
- Final files are `sort -V | uniq`-ed CIDR-per-line text

Sources fall into two patterns: (1) vendor-published JSON/TXT + `jq` (Google, AWS, OpenAI, Cloudflare); (2) `dig`-resolution of a hardcoded domain list (Devolutions, Wispr Flow, Tana, Sunsama, most newer providers). Many combine both.

## Common commands

System deps once:

```bash
sudo apt install -y whois parallel gawk dnsutils jq
pip install -r utils/requirements.txt
```

Run a single provider's downloader (from inside the provider dir — preferred for local iteration):

```bash
cd google && bash downloader.sh
```

…or from the repo root (matches the GitHub Action):

```bash
bash google/downloader.sh
```

Regenerate `_merged.txt` for one provider:

```bash
python utils/merge.py --source=google/ipv4.txt | sort -V > google/ipv4_merged.txt
python utils/merge.py --source=google/ipv6.txt | sort -V > google/ipv6_merged.txt
```

Refresh the auto-generated parts of the README:

```bash
python utils/render_readme.py          # rewrites in place
python utils/render_readme.py --check  # CI guard — exits non-zero if it would change anything
```

Reproduce the full workflow locally:

```bash
find . -name downloader.sh | sort -h | awk '{print "Executing "$1"...";system("bash "$1)}'
cat $(find . -name ipv4.txt | sort -h) | sort -V | uniq > all/ipv4.txt
cat $(find . -name ipv6.txt | sort -h) | sort -V | uniq > all/ipv6.txt
find . -name ipv4.txt | sort -h | parallel --will-cite -j 1 python utils/merge.py --source={} '|' sort -V '>' {.}_merged.txt
find . -name ipv6.txt | sort -h | parallel --will-cite -j 1 python utils/merge.py --source={} '|' sort -V '>' {.}_merged.txt
python utils/render_readme.py
```

Trigger the production update on demand: GitHub Actions → "Update" workflow → Run workflow.

## Adding a new provider

1. Create `<provider>/downloader.sh` following the contract above. Use [devolutions/downloader.sh](devolutions/downloader.sh) as a template for the dig-based pattern, or [google/downloader.sh](google/downloader.sh) for a JSON-based pattern.
2. Run it once locally from inside the provider dir to seed `ipv4.txt` / `ipv6.txt`. The `_merged.txt` files don't need to be created by hand — the workflow generates them — but committing initial versions keeps the repo state consistent.
3. Add an entry to [utils/providers.json](utils/providers.json) (kept in alphabetical order by `dir`). Optional `note` field shows up in the README's Notes column.
4. Run `python utils/render_readme.py` to refresh the README table.
5. The `all/` aggregate and the cron schedule pick up the new provider automatically — no workflow edits needed.
